# 词表源文件写作规范（dsh-ct-norm）

本目录下的 `*.json` 是**人工整理**的「中文 CT 报告自由描述 → MeSH 概念」词表源文件。
它们**不是**插件运行时读取的文件：运行时读的是构建产物
（`data/ct.lexicon.jsonl` + `data/mesh.subset.jsonl`），由
`build-ct-lexicon.mjs` 从本目录的源文件生成。

构建脚本会做四件事，任何一条不过就**构建失败**（这是本插件诚实性的地基）：

1. 把每个条目的 MeSH 字段（MeSH **英文规范名**）拿去 NLM 的 MeSH 2026 索引里反解；
   反解不到、或反解出多个义项而无法确定 → 报错退出。
2. 取反解出的**描述符记录**，把规范名、MeSH 编号（`D######`）、树号、释义一并写进
   `data/mesh.subset.jsonl`。
3. 全局查重：同一个中文/英文别名不得出现在两个条目里。
4. 校验 `ct.rules.json` 里「未归一化征象」的写法不与词表条目冲突。

> **为什么源文件里只写 MeSH 英文规范名、不写编号？**
> 因为编号一旦由人写，就有编造的可能；而规范名由机器去 NLM 索引反解，
> 反解不到就直接失败。这样「归一化输出里的每一个 MeSH 编号都来自 NLM 索引」
> 就成了构建期的不变量，而不是一句口头承诺。
> 连 `note` 里也不许写编号——note 会随包分发并显示给用户。

## 1. 条目 schema

```json
{
  "id": "pleural-effusion",
  "kind": "finding",
  "mesh": "Pleural Effusion",
  "region": "chest",
  "zh": ["胸腔积液", "胸膜腔积液", "胸腔内积液", "胸水"],
  "en": ["pleural effusion", "hydrothorax"],
  "approx": ["胸水"],
  "note": "可选的人工说明"
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 短横线 slug，**全局唯一**，按字母序排列。规则文件与测试会引用它，改名即破坏兼容 |
| `kind` | ✅ | `anatomy` / `finding` / `neoplasm` / `assessment` / `imaging` / `morphology` |
| `mesh` | ✅（`morphology` 的 `mass`/`nodule`/`lesion` 除外） | MeSH **英文规范名**，必须逐字出现在 [`mesh-allowlist.txt`](mesh-allowlist.txt) 里 |
| `zh` | ✅ | 中文别名，至少 1 个（解剖段如「升结肠」可只有 1 个），其余类别建议 ≥3 个 |
| `en` | ⬜ | 0–4 个英文写法，**全小写**；允许空格与连字符（`non-small cell lung carcinoma`） |
| `approx` | ⬜ | 近似映射的别名列表（见 §3）。**推荐写成列表**，不要写 `true` |
| `neoplasm` | ⬜ | **仅 `kind=anatomy`**：该部位的肿瘤规范名（须在白名单的「部位 → 肿瘤」段里），供组合规则用 |
| `region` | ⬜ | `chest` / `abdomen` / `pelvis` / `head-neck` / `msk` / `neuro` / `vascular` / `systemic` / `imaging` |
| `note` | ⬜ | 给人看的说明，不参与匹配。**不得含 MeSH 编号** |

### 仅 `kind=morphology` 使用的字段

| 字段 | 说明 |
| --- | --- |
| `action` | 组合规则：`metastasis` / `neoplasm` / `mass` / `nodule` / `lesion` / `recurrence` |
| `lymphaticMesh` | `action=metastasis` 且部位是淋巴结时改用的更精确概念（如 `Lymphatic Metastasis`） |
| `candidates` | `action=nodule` 时按数量二选一的两个概念（`single` / `multiple`） |
| `siteCandidates` | 「部位 MeSH 名 → 概念 MeSH 名」的查表。用于「甲状腺右叶结节」这类**中间夹了修饰词、字面别名接不上**的写法 |

## 2. 中文别名（`zh`）的要求

这是整个插件的价值所在，也是最容易写坏的地方：

1. **必须是真实写法。** 只写中文 CT 报告里真的会出现的词，不要写教科书生造词、
   不要写英文直译式中文（「胸膜的渗出」）。参考语感：
   「右肺上叶见一结节影，边缘毛糙，考虑周围型肺癌可能」。
2. **不要带标点、空格、数字、单位。** 数字与单位属属性层（尺寸由 `sizePattern` 抽）。
3. **单个别名 2–12 个汉字**；英文别名 ≤48 字符。
4. **全局唯一。** 同一别名不得出现在两个条目里——包括「归一化后等价」的情况。
   判定归谁：**更特异的归更特异的条目**（`淋巴结肿大` 归 `Lymphadenopathy`，
   `淋巴结` 归 `Lymph Nodes`；两者不冲突，匹配按最长优先）。
5. **不要收录泛化形态学词**（`癌` / `肿瘤` / `占位` / `转移` / `结节` 等），
   它们由 `50-morphology.json` 与组合规则统一处理，写进具体条目会导致过度命中。
6. **含修饰词/极性词不一定是错**——见 §4。

## 3. 概念选词的要求

1. **一个条目 = 一个 MeSH 概念。** 不要把两个概念塞进一个条目。
2. **MeSH 里没有的概念，不要硬凑。** 影像描述性征象（磨玻璃影、毛刺征、分叶、
   低密度灶、强化、钙化、壁增厚…）**不属于 MeSH 主题词粒度**，它们统一进
   `data/ct.rules.json` 的 `unmapped` 清单，作为「未归一化」如实报出。
   这一条是本插件区别于「什么都敢映射」的关键。
3. **宁愿不收，也不要错收。** 一个错的映射比十个漏收危害大得多。
4. **近似就要标。** 若某中文写法与 MeSH 概念的**外延不一致**（更宽、更窄、或只是描述性说法），
   必须把该写法列进 `approx`：

   ```json
   { "mesh": "Abscess", "zh": ["脓肿", "脓腔", "化脓性病变"], "approx": ["化脓性病变"] }
   ```

   判据是「外延是否一致」：

   | 写法 | 目标概念 | 标近似？ | 为什么 |
   | --- | --- | --- | --- |
   | 脓肿 | Abscess | ❌ | 外延一致 |
   | 化脓性病变 | Abscess | ✅ | 比 Abscess 宽，可含蜂窝织炎 |
   | 肺癌 | Lung Neoplasms | ❌ | 外延一致 |
   | 肺门肿块 | Lung Neoplasms | ✅ | 肺门团块也可能是肿大淋巴结或血管影 |
   | 硬膜下血肿 | Intracranial Hemorrhages | ✅ | 是它的下位概念 |

   ⚠ **不要把 `approx` 写成 `true`。** 那等于把整条条目所有别名（包括「脓肿」这种精确对应）
   都打上「近似」警示——这是**假的警示**，会让人对该信的地方不信任。
   构建脚本会把 `true` 展开成完整别名列表，并当作提醒事项报出来。

5. **不用怕「漏收」被看到。** `unmapped` 清单（`ct.rules.json`）就是给漏收准备的：
   把一个有意义但 MeSH 没有对应概念的写法收进去，附一句 `reason`，工具会如实报出来。
   这比硬塞一个编号有用得多。

## 4. 修饰词与极性词：两条匹配通道

运行时匹配前会从「骨架文本」里摘掉两类词：

* **修饰词**：程度（少量/明显）、数量（多发/单发）、侧别（左/右/双侧）、变化（较前/新发）、
  以及可见/显示/呈/见；
* **极性词**：否定（未见/无/排除/阴性）、不确定（考虑/可能/不除外/待排）。

因此写法 `胸腔积液` 能匹配上原文的「右侧胸腔**少量**积液」。**但**有些别名本身含这些词，
而且中文里没有别的写法可选：

```
无病生存 / 无进展生存 / 无病生存期     ← 含「无」
多发性骨髓瘤                          ← 含「多发」
弥漫性甲状腺肿                        ← 含「弥漫」
```

这类别名由 `lib/lexicon.js` 的**「原文匹配」通道**处理，照常能命中。
构建会给一条提示（不是错误），提示你能不能用不含修饰词的等价写法——不能用就留着：

| 写法 | 能否去掉修饰词 | 处置 |
| --- | --- | --- |
| 右侧胸腔积液 | 能（`胸腔积液` 已收录） | 别收 |
| 多发结节 | 能（`结节` + 数量属性） | 别收 |
| 无病生存 | **不能** | 保留，走原文通道 |

**唯一会被判错的是「整条别名全由这些词组成」**（如 `少量`、`未见`），那等于没写内容。

## 5. 文件分工

| 文件 | 负责范围 |
| --- | --- |
| `10-anatomy.json` | 解剖部位（`kind=anatomy`），带 `neoplasm` 组合目标 |
| `12-findings-head-neck.json` | 头颈部征象（甲状腺结节、甲状腺肿…） |
| `20-findings-thorax.json` | 胸部征象与病变 |
| `30-findings-abdomen.json` | 腹盆腔征象与病变 |
| `40-findings-neuro-msk.json` | 神经 / 骨肌 / 血管 / 全身性征象 |
| `45-urogenital-assessment.json` | 泌尿生殖征象 + 疗效评估与检查方法 |
| `50-morphology.json` | 泛化形态学词（癌 / 转移 / 占位 / 结节…），供组合规则使用 |
| `55-neoplasms-histology.json` | 具体组织学类型与瘤种（腺癌、肝细胞癌、淋巴瘤、骨肉瘤…） |
| `ct.rules.json`（在上一级） | 否定 / 可疑 / 程度 / 数量 / 侧别 / 尺寸 / 变化 词表 + 未归一化征象词表 |

## 6. 提交前自检

```powershell
node build-ct-lexicon.mjs --check   # 只校验，不写产物
node test-ct-norm.mjs               # 创建产物后跑全套；第 14 节会逐别名验证能否命中
```

构建脚本会打印每个条目的反解结果、全部查重冲突与提醒事项，按提示修即可。
**改完源文件一定要重跑构建**，否则 `ct.manifest.json` 里的 sha256 会对不上，
测试第 1 节与打包脚本都会拦下。
